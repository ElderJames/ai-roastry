# 需求文档：多 Agent 编排框架

## 简介

本项目旨在为 `llm-pool` 框架构建一个先进的多 Agent 编排功能。该功能允许将现有的 `LlmApp` 实体升级为具备高级推理和工具使用能力的自主 Agent，并支持它们通过可配置的流程协同工作，以完成单个 Agent 难以处理的复杂任务。

---

## 1. Agent 核心能力

### 1.1. Agent 实体定义
- **用户故事**: 作为一个开发者，我希望将一个 `LlmApp` 封装成一个标准的 `Agent` 实体，以便它能被统一编排和管理。
- **需求**:
    - **REQ-AGENT-101**: 系统**应**提供一个新的 `Agent` 实体，该实体**应**与一个 `LlmApp` 关联，以继承其基础指令和角色设定。
    - **REQ-AGENT-102**: `Agent` 实体**应**包含 `Name`、`Description` 和 `Instructions` 字段，用于覆盖或补充来自 `LlmApp` 的设定。
    - **REQ-AGENT-103**: 系统**应**提供一个管理界面，用于创建、查看、更新和删除 `Agent` 实体。

### 1.2. ReAct 推理与工具调用
- **用户故事**: 作为一个 Agent，我希望能像人一样“思考-行动”，通过调用工具来获取信息或执行操作，以完成我的任务。
- **需求**:
    - **REQ-AGENT-201**: 当 Agent 被调用时，它**应**能够执行一个 ReAct (Reason-Act) 循环，直到任务完成或达到限制。
    - **REQ-AGENT-202**: 在 ReAct 循环的“思考”阶段，Agent **应**能根据对话历史和初始目标，生成一个包含下一步行动（是调用工具还是回复用户）的计划。
    - **REQ-AGENT-203**: 在 ReAct 循环的“行动”阶段，如果计划是调用工具，系统**应**能准确地执行指定的工具并获取返回结果。
    - **REQ-AGENT-204**: Agent **应**能将工具的返回结果作为新的上下文，进入下一轮“思考”阶段。
    - **REQ-AGENT-205**: 如果 Agent 的底层模型不支持 Tool Calling 或 Function Calling，系统**应**优雅地降级，仅提供基于文本的问答能力。

### 1.3. 动态工具集
- **用户故事**: 作为一个开发者，我希望能为 Agent 灵活地配置可用的工具，包括内部代码和外部服务。
- **需求**:
    - **REQ-AGENT-301**: 系统**应**允许将任何实现了特定接口的内部服务或方法注册为“内部工具”。
    - **REQ-AGENT-302**: 系统**应**提供一个通用的“MCP 工具调用器”，使其能够与任何符合模型上下文协议 (MCP) 的外部服务交互。
    - **REQ-AGENT-303**: 系统**应**提供一个新的 `McpServerConfig` 实体，用于持久化存储外部 MCP 服务的元数据（名称、URL、描述等）。
    - **REQ-AGENT-304**: 系统**应**提供一个管理界面，用于增删改查 `McpServerConfig`。
    - **REQ-AGENT-305**: 在 Agent 的配置界面，用户**应**可以从所有已注册的“内部工具”和“MCP 工具”列表中，为该 Agent勾选其可用的工具。

### 1.4. 上下文与记忆工具
- **用户故事**: 作为一个 Agent，我希望有一个“草稿板”来记录长对话中的关键信息，避免遗忘，并节省 Token。
- **需求**:
    - **REQ-AGENT-401**: 系统**应**提供一个名为 `ContextExtractor` 的内置工具。
    - **REQ-AGENT-402**: 当 `ContextExtractor` 工具被调用时，它**应**在一个后台线程中异步执行，以避免阻塞主流程。
    - **REQ-AGENT-403**: `ContextExtractor` **应**能获取当前的对话历史，并使用一次独立的 LLM 调用来总结关键信息。
    - **REQ-AGENT-404**: 总结后的信息**应**被存储在一个与当前会话关联的“记忆存储”中（例如，一个简单的键值对缓存或数据库表）。
    - **REQ-AGENT-405**: 系统**应**提供一个 `MemoryQuery` 工具，允许任何 Agent 在后续步骤中查询这份“记忆存储”，以获取精炼后的上下文。

## 2. Agent 编排

### 2.1. 编排流程定义
- **用户故事**: 作为一个应用管理员，我希望能通过界面来设计和定义一个由多个 Agent 组成的协作流程。
- **需求**:
    - **REQ-ORCH-101**: 系统**应**提供一个新的 `AgentGroup` 实体，用于定义一个编排流程。
    - **REQ-ORCH-102**: `AgentGroup` **应**包含一个 `OrchestrationMode` 字段，支持 `Sequential`（顺序）和 `GroupChat`（群聊）两种模式。
    - **REQ-ORCH-103**: 系统**应**提供一个新的 `AgentGroupMember` 实体，用于将一个 `Agent` 添加到 `AgentGroup` 中，并定义其在该流程中的角色或顺序。
    - **REQ-ORCH-104**: 系统**应**提供一个管理界面，用于创建、配置和管理 `AgentGroup` 及其成员。

### 2.2. 编排服务执行
- **用户故事**: 作为一个开发者，我希望能通过调用一个服务来执行一个预定义的 Agent 编排流程。
- **需求**:
    - **REQ-ORCH-201**: 系统**应**提供一个 `AgentOrchestratorService` 服务。
    - **REQ-ORCH-202**: 该服务**应**提供一个 `InvokeAsync(string agentGroupId, string userInput)` 方法，用于启动并执行指定的编排流程。
    - **REQ-ORCH-203**: 在 `Sequential` 模式下，前一个 Agent 的最终输出**应**作为后一个 Agent 的输入。
    - **REQ-ORCH-204**: 在 `GroupChat` 模式下，所有 Agent **应**共享同一个对话历史，并根据预设的发言策略（如轮流、自动选择）进行多轮交互。
    - **REQ-ORCH-205**: `AgentGroup` 的配置中**应**包含一个终止条件，例如最大交互轮次或一个用于判断是否结束的 Agent/Function，以防止无限循环。
    - **REQ-ORCH-206**: 编排流程执行完毕后，`InvokeAsync` 方法**应**返回一个包含最终结果和执行摘要的响应对象。

### 2.3. API 接入
- **用户故事**: 作为一个外部应用，我希望能通过一个简单的 HTTP 请求来调用一个 Agent 编排流程。
- **需求**:
    - **REQ-API-101**: 系统**应**提供一个新的 API 端点 `POST /v1/agent-groups/{groupId}/invoke`。
    - **REQ-API-102**: 该端点的请求体**应**包含用户输入（`input`）和其他可选参数。
    - **REQ-API-103**: 该端点在内部**应**调用 `AgentOrchestratorService.InvokeAsync` 方法来执行流程。
    - **REQ-API-104**: 该端点**应**在流程执行完成后，返回一个包含最终结果的 JSON 响应。
